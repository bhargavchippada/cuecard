# Workflow and process rules for evaluation

Classify every task as SIMPLE, MEDIUM, or COMPLEX before starting — state the assessment explicitly with reasoning
SIMPLE tasks (1-2 files, low risk) can proceed without a plan — just implement and verify
MEDIUM tasks (3-10 files) require an inline plan, research, tests alongside code, and agent review after implementation
COMPLEX tasks (10+ files, architecture changes) require a full PRD written to artifacts/ before any implementation begins
Review PRDs with multiple specialist subagents (architect, security, database, code quality) in parallel before implementing
Run iterative PRD reviews until a round comes back clean — typical convergence is 4 rounds
Never implement a feature without reading 2-3 similar files in the codebase first to understand existing patterns
Use the planner agent for complex features, architect agent for system design decisions, tdd-guide agent for new features and bug fixes
Launch parallel subagents for independent review tasks — never run them sequentially when they can run simultaneously
Run code review with 3 parallel agents (code-reviewer, security-reviewer, python-reviewer) and iterate until clean
Keep running review rounds until two consecutive rounds produce zero CRITICAL, HIGH, or MEDIUM findings — never use a fixed round count
Delegate implementation to worker agents via tmux sessions and monitor progress with cron-based polling
Tell delegated agents to report back via tmux send-keys to your session instead of polling for completion
Monitor agent context usage in tmux — compact when context remaining drops below 67 percent
Write tests before implementation following TDD red-green-refactor cycle
Require 100 percent test coverage on all new code — not 80 percent, not 90 percent, always 100 percent
Validate every phase against real data before moving to the next phase — synthetic tests alone are insufficient
Manually inspect LLM output after every classification wave — read actual output, do not trust confidence scores
Always benchmark a single LLM call before launching a full pipeline run — a 2-second PING test can save hours
If a single LLM call takes more than 5 seconds for a trivial prompt, investigate SDK overhead before proceeding
Establish baseline metrics before implementing any improvement — you cannot claim X is better without before/after numbers
Never trust small sample benchmark results — run the full dataset before drawing conclusions
Never build infrastructure around unproven techniques — test hypotheses in controlled experiments first, implement only winners
Fix the pipeline stage that produces bad output, do not patch the output with manual rules downstream
Each pipeline stage must be independently high quality — do not rely on downstream stages to rescue upstream failures
Use lightweight deterministic approaches first, add LLM stages only when they demonstrably improve quality
When schema or cardinality changes, audit every consumer (views, queries, CLI, exports, tests) before implementing
After the parallel LLM phase, retry failed items sequentially one at a time to avoid rate limiting contention
After every batch LLM response, diff sent IDs against returned IDs to detect silently dropped items
Use semantic similarity (embeddings or LLMs) for text deduplication — never use lexical or word-based matching
Save LLM-generated artifacts (pickles, checkpoints) before overwriting — never destroy a baseline during experiments
Store all predictions, reasoning, and grounding in benchmark results for later reanalysis — not just numeric scores
Before compaction, save task state to artifacts/ including what was done, what remains, key decisions, and blockers
Update CLAUDE.md when project structure, architecture, or conventions change during a session
Update README when user-facing behavior, setup steps, or dependencies change
Use conventional commit format with types feat, fix, refactor, docs, test, chore, perf, ci
Run security review before every commit — check for hardcoded secrets, SQL injection, XSS, missing input validation
For new libraries or APIs, research alternatives, verify documentation, audit maintenance status, and benchmark before adopting
Search GitHub for existing implementations and proven patterns before writing anything from scratch
Use Context7 for library documentation lookups, Exa for broader web research, mgrep for semantic code search
When a tool or command fails, read the full error message and search project docs before retrying — never retry blindly
After 2 failed fix attempts on the same error, stop and ask the user for guidance instead of spiraling
Filter pipeline noise at multiple independent stages with configurable thresholds — no single filter point
When running A/B benchmark comparisons on LLM artifacts, use the same pre-built artifact and change only one variable
Run the original paper code first when reproducing published results — do not theorize about score gaps without evidence
Score gaps between models on routine tasks usually indicate code or config differences, not model quality differences
