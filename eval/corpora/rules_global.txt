# === TOOL_USE (constrains specific tool actions) ===
When writing code that executes strings as commands: never use eval(), exec(), or shell=True — these execute arbitrary input as code, enabling remote code execution attacks
When creating or writing sensitive files (keys, configs, tokens, .env, credentials) via Bash or Write: set file permissions to 0o600 — world-readable secrets are the most common cloud breach vector
When running Python package commands (Bash): use uv instead — pip doesn't respect lock files, creates inconsistent environments, and lacks dependency resolution
When writing try/except or catch blocks (Edit, Write): always handle errors explicitly — empty catch blocks hide bugs that surface later as mysterious failures with no stack trace
When writing code that opens files, database connections, or HTTP sessions (Edit, Write): always close them after use — unclosed resources leak memory and exhaust connection pools, eventually crashing the service
When writing code with hardcoded configuration values (Edit, Write): use environment variables instead — hardcoded config prevents deployment to different environments and leaks secrets into source control
When writing functions that receive mutable arguments (Edit, Write): never mutate function arguments or shared state — mutations cause action-at-a-distance bugs where changing one variable silently breaks code elsewhere
When running git commit (Bash): use conventional commit format (feat:, fix:, refactor:, docs:, test:) — without structured messages, changelogs are impossible to generate and git blame is useless
Never force-push to main or master branch — force-push overwrites other developers' commits with no recovery path
When running build commands or adding generated output directories: add .gitignore entries for generated files and build artifacts — committed artifacts bloat the repo and cause merge conflicts on every build
Always append Enter after tmux send-keys text — without it the text is pasted into the prompt but never submitted, so the target session never receives or executes the message
When searching for library docs, API usage, or code patterns (WebSearch, Bash: grep, mgrep): use Context7 for library docs, Exa for web research, mgrep for semantic code search — wrong search tool returns irrelevant results and wastes time on false leads
When a function exceeds 50 lines (Edit, Write): split it — large functions hide bugs in nested logic, and large files make it impossible to understand scope of changes. Keep files under 800 lines (400 preferred)
When writing error handling, try/except, or fallback logic (Edit, Write): never use silent fallbacks — if a pipeline stage falls back to an alternative, log it loudly and surface it in the output so the user knows the result is degraded, not just different
When calling external APIs: log every call with latency, status code, and response size — without observability, production debugging becomes guesswork and intermittent failures go undetected
When fetching external data: cache expensive results with explicit TTL — stale cache corrupts downstream analysis, and no cache makes the system unusably slow
When writing new classes or module interfaces (Edit, Write): design interfaces as Protocols — concrete implementations can be swapped without refactoring callers, enabling testing with fakes and future provider changes without cascading code changes
When composing scores from multiple signals, separate direction from magnitude — multiplying direction × confidence double-counts the signal and produces near-zero results for uncertain inputs
When writing code that parses API responses or external data (Edit, Write): use a fallback chain with NaN-safe extraction — API column names are unstable across providers, and float(NaN) is truthy so `value or default` silently passes NaN through
When writing data models, schemas, or dataclasses (Edit, Write): make them accept defaults for optional data sources — crypto has no income statements, new companies have no history — hardcoded required fields silently exclude valid use cases
When writing unit tests that involve LLM calls, HTTP requests, or subprocesses (Edit, Write test files): always mock external calls — real calls make tests slow, flaky, and non-deterministic; 18-minute test suites get skipped
When writing test functions that call code with background tasks or HTTP clients (Edit, Write test files): never let a test trigger a real background task or HTTP request — mock at the boundary so the test exercises YOUR code, not the external service
Mark tests that require real services with @pytest.mark.slow or @pytest.mark.e2e and exclude them from the default test run — the default `pytest` invocation must always be fast, deterministic, and offline
If a single test takes more than 1 second, it is either testing too much or hitting a real service — split it or mock the slow dependency
When writing test code with async operations or waits (Edit, Write test files): never use time.sleep() — use mock clocks, manual event triggers, or synchronous test helpers instead, because sleep-based tests are both slow and flaky
When using llama-server with -np N parallel slots, total context is divided by N — ensure every prompt fits within (total_ctx / np) tokens per slot, because exceeding it returns a cryptic 400 error with no useful diagnostic
When LLM JSON parsing fails, retry up to 2 times before falling back — intermittent parse errors from code fences or formatting are recovered by a simple retry; three consecutive failures indicate a prompt problem, not a fluke
When starting feature work (Bash: git checkout, git branch): always create a new branch — working directly on main risks breaking the shared branch and makes it impossible to review changes in isolation
When writing or editing public functions, classes, or methods (Edit, Write): document all public API functions with docstrings — undocumented functions force every caller to read the implementation, multiplying onboarding time and causing misuse
When writing form handlers or state-changing API endpoints (Edit, Write): enable CSRF protection — without it, malicious sites can trigger actions on behalf of authenticated users via forged requests
When writing code with literal numbers: extract magic numbers into named constants — unnamed numbers scattered through code are impossible to find, update consistently, or understand
Before committing code: remove console.log, print(), and debug statements — debug output clutters logs, leaks internal state, and makes real errors harder to find in production monitoring
When writing data structures or containers (Edit, Write): prefer immutable data structures over mutable ones — immutable data prevents hidden side effects, makes debugging easier, and enables safe concurrency
When writing code that renders user content as HTML (Edit, Write templates, frontend components): sanitize all HTML output — unsanitized user content lets attackers inject scripts that steal session tokens, redirect users, or deface the page
When writing concurrent I/O code with threads (Edit, Write): use asyncio instead — threads add GIL contention, race conditions, and debugging complexity while asyncio handles thousands of concurrent I/O operations in a single thread
When writing dataclasses or data containers (Edit, Write): use frozen dataclasses (frozen=True) for immutable data — mutable dataclasses allow accidental field modification that causes action-at-a-distance bugs, while frozen dataclasses fail fast on mutation attempts
When writing database queries with string interpolation or concatenation (Edit, Write): use parameterized queries instead — string-interpolated queries let attackers modify the query structure, read arbitrary data, or delete tables
When writing or editing function definitions (Edit, Write, def, async def): use type hints on all function signatures — untyped functions force callers to read the implementation and prevent static analysis from catching type errors before runtime
After the parallel LLM phase, retry failed items sequentially one at a time to avoid rate limiting contention
After every batch LLM response, diff sent IDs against returned IDs to detect silently dropped items
When writing deduplication logic for text data (Edit, Write): use semantic similarity (embeddings or LLMs) — never use lexical or word-based matching, because paraphrases and synonyms are invisible to string comparison
When about to overwrite model artifacts or baseline files: save a copy first — non-deterministic pipelines cannot reproduce the exact same output
Use "reasoning-first" JSON: {"reasoning": "...", "signal": "..."} not {"signal": "...", "reasoning": "..."} — field order in JSON prompts determines whether the model thinks before deciding; this is the cheapest quality upgrade available
Always include an example JSON object in the prompt — models that see the exact format they should produce have near-zero parse errors; without an example, they improvise with markdown fences and free text

# === WORKFLOW (guides process decisions) ===
When discovering exposed credentials in code, logs, or git history (Bash: git log, git diff, Read): rotate any secrets that may have been exposed — exposed credentials remain valid until rotated, giving attackers a persistent access window
Delegate implementation to worker agents via tmux sessions and monitor progress with cron-based polling
Tell delegated agents to report back via tmux send-keys to your session instead of polling for completion
Monitor agent context usage in tmux — compact when context remaining drops below 67 percent
Before moving to the next implementation phase: validate the current phase against real data — synthetic tests pass when the real thing fails because mocks diverge from production
Before implementing any improvement or optimization: establish baseline metrics first — without before/after numbers you cannot distinguish real improvement from noise
When reviewing a PRD or design document: use multiple specialist subagents (architect, security, code quality) in parallel — a single reviewer misses entire categories of issues
After each review round: keep running until two consecutive rounds produce zero CRITICAL/HIGH/MEDIUM findings — fixed round counts stop too early or too late
Before writing new utility code or implementing a common pattern: search GitHub first — 80% of problems are already solved with battle-tested code
When debugging poor output quality: fix the upstream pipeline stage, not downstream patches — downstream fixes accumulate into unmaintainable complexity
When building multi-stage pipelines: ensure each stage is independently high quality — downstream stages cannot rescue upstream failures
When an LLM outputs confidence scores or probabilities: don't trust them — use evidence counts, ensemble agreement, or track record instead
Before building on an unvalidated dependency: spike-test it for 2 hours — discovering a library fails after building 3 layers on top wastes days
Prefer mature extensible frameworks over building from scratch — if LangGraph, FastAPI, or similar battle-tested projects provide the feature (routing, checkpointing, streaming), use them even if a simpler stdlib approach works today, because refactoring from simple to framework later costs more than starting with the framework
Reuse popular open-source components for each layer of the system — only build custom code for what doesn't exist, because mature projects provide stability, community support, and extensibility that hand-rolled code cannot match
After mocked tests pass: test with real external data — NaN values, missing columns, and API format differences only surface with live data
When launching subagents: set explicit scope boundaries and kill stale ones — unbounded reviewers find infinite speculative findings
When model predictions look wrong: audit the ground truth first — wrong fixture expectations are indistinguishable from model failures, and removing them is a free quality improvement
When writing rules or instructions for agents: explain consequences, not just commands — agents follow rules they understand but ignore rules that just say what to do
Before trusting benchmark results: verify the evaluation methodology — if you benchmark model A against model B's artifacts, model B wins by default
After each implementation milestone: run convergence reviews with parallel code + security agents — per-phase reviews catch bugs when they're cheap to fix
After revising a PRD or design document: run convergence reviews — design gaps that survive review become implementation bugs that survive testing
Before testing a completed milestone: create a comprehensive test plan reviewed by subagents — an incomplete test plan produces false confidence
For any significant feature: follow the three-layer gate — PRD + reviews, then implementation + reviews, then test plan + reviews — skipping any layer compounds risk
When choosing LLM reasoning mode: thinking mode costs 10x but is most decisive; reasoning-first JSON recovers 80% of quality at 3x speed — match compute to difficulty
Classify every task as SIMPLE, MEDIUM, or COMPLEX before starting — state the assessment explicitly with reasoning
When receiving a task touching 1-2 files (config change, small fix): proceed without a plan — simple tasks don't need overhead
When receiving a task touching 3-10 files: create an inline plan with research, write tests alongside code, and run agent review after — medium tasks need structure
When receiving a task touching 10+ files or requiring new architecture: write a full PRD first — complex tasks without specs produce rework and missed requirements
When starting complex features: use the planner agent; for system design: use architect; for new features/bugs: use tdd-guide — match the agent to the task type
When multiple independent review or analysis tasks exist: launch parallel subagents — sequential execution wastes time when tasks don't depend on each other
After writing code: run 3 parallel review agents (code-reviewer, security-reviewer, python-reviewer) and iterate until clean
When reviewing PRDs: iterate rounds with specialist agents until a round comes back clean — each round finds issues at a different depth
Manually inspect LLM output after every classification wave — read actual output, do not trust confidence scores
Never trust small sample benchmark results — run the full dataset before drawing conclusions
Never build infrastructure around unproven techniques — test hypotheses in controlled experiments first, implement only winners
Use lightweight deterministic approaches first, add LLM stages only when they demonstrably improve quality
When saving benchmark results: store predictions, reasoning, and grounding — not just numeric scores — for later reanalysis when methodology changes
When building retrieval pipelines: filter noise at multiple independent stages with configurable thresholds — no single filter point can handle all query types
Before compaction, save task state to artifacts/ including what was done, what remains, key decisions, and blockers
When running A/B benchmark comparisons on LLM artifacts, use the same pre-built artifact and change only one variable
When reproducing published results: run the original paper code first — do not theorize about score gaps without evidence from the reference implementation
Score gaps between models on routine tasks usually indicate code or config differences, not model quality differences
After 2 failed fix attempts on the same error, stop and ask the user for guidance instead of spiraling

# === BOTH (constrains tools AND guides process) ===
When running git add or git commit, or writing config/.env files: never include secrets — once pushed, secrets are in the history forever and require rotation across all environments
When writing API endpoints, form handlers, or CLI parsers: validate all user input at system boundaries — unvalidated input propagates corrupted data through the entire system, causing failures far from the source
When running git commit or git push after writing new code: require 100% test coverage on all new code — uncovered code is untested code, and untested code breaks silently in production
Before running a batch LLM pipeline: benchmark a single call first — a 2-second PING test saves hours of wasted compute when the endpoint is misconfigured or slow
When running git commit or git add on Python files: run ruff check and mypy first — type errors and lint violations caught at commit time cost 10 minutes to fix, but in production they cost hours to debug
When editing code that changes CLI commands, API endpoints, setup steps, or adding new dependencies (Edit, Write): update README to match — outdated README causes every new contributor to fail on setup
Before creating a new file or writing a new module (Write, Edit): read 2-3 similar files in the codebase first — introducing a second pattern where one exists creates permanent inconsistency that confuses every future reader
When a tool fails, read the full error and search docs before retrying — blind retries waste time and hide the root cause, while the fix is usually in the error message
When finishing an implementation phase or milestone (Bash: git commit): commit after each phase — atomic tested commits prevent compound debt, enable bisection for regressions, and give reviewers digestible chunks instead of monolithic diffs
When running pytest or the test suite (Bash: pytest, uv run pytest): the full unit test suite must complete in under 5 seconds — if it takes longer, something is unmocked; investigate immediately, don't normalize slow tests
When writing or modifying daemon/server code that provides a fast path (Edit, Write serve.py, daemon code): verify the fast path exercises the same code paths as the inline path — daemon shortcuts silently bypass features that work in direct mode, making core features inoperative in production
When extending a system to support new event types or modes, grep for every call site that dispatches on the old set — hardcoded event lists (e.g. a 2-event frozenset) silently reject new events instead of erroring, and the failure appears as "feature doesn't work" not "event rejected"
When adding new dependencies: review all dependencies for known vulnerabilities first — a vulnerable dependency in your supply chain is an open door that attackers actively scan for
When running git commit (Bash): run quality checks (lint, type check, tests) before every commit — catching failures at commit time prevents broken code from reaching shared branches where it blocks the entire team
When starting a new feature or bug fix (Edit, Write new code): write tests before implementation (TDD red-green-refactor) — writing tests first forces you to define the interface before the implementation, catches design issues early, and guarantees every feature has a test
When adding a new library or API dependency: research alternatives, verify documentation, audit maintenance status, and benchmark before adopting — unvetted dependencies become permanent tech debt
After changing project structure, architecture, or conventions: update CLAUDE.md — without this, the next session starts with stale context and makes wrong assumptions
When a tool call or LLM response takes 10x longer than expected: investigate immediately — normalized slowness compounds across thousands of calls
When schema or cardinality changes, audit every consumer (views, queries, CLI, exports, tests) before implementing
